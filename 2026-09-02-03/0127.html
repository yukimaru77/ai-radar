LINUX DO gossip。@cld。posts 7 / likes 1。Codex を中転 API に繋ぐと、文脈圧縮がキャッシュヒットしない、なぜ誰も言わない、という問い。スクショ2枚。

用語の切り分け。@mintaqrua は文脈圧縮は本来 cache を hit しない（reasoning と tool call を切るから）、ただし 240k は高い、encrypted compaction か。cld は reasoning/tool の剪裁は別手段（OpenClaw にある記憶）、ここで言う圧縮は閾値後に現行モデルが要約プロンプトでまとめ、新セッションに Harness 预设を入れ、要約をユーザ文脈にする方式。Codex も Claude Code もこの方案、と cld。

実測。Trinix は CPA 反代はずっとキャッシュがある。cld は Claude Code はヒット、Codex はヒットしない。どちらが得か（切って入力を減らす vs 圧縮してキャッシュ）は未決。

mintaqrua の追記：Codex の encrypted compaction は CC の prompt based と全く違う。長距離タスクの強み。制限は provider name が OpenAI か Azure 必須、それ以外は性能が落ちる。大半の中転はこの機能をサポート。

設定例（スレ原文）：

[model_providers.custom_api] name = "Azure" base_url = "<url>/v1" wire_api = "responses"

ソースを見た範囲では compaction は reasoning を捨てないので cache miss は奇妙。圧縮用にモデルを差し替えている可能性。luna を sol に替える、ということは普通ない、と。

cld「Codex 接入中转API 后上下文压缩不会命中缓存, 为什么没人提这个事?」

cld「我说的上下文压缩是指达到上下文阈值后由当前模型根据压缩提示词进行总结。然后开启新会话，填充好 Harness 预设的上下文后，将这次的总结作为新的用户上下文。 已知目前 codex 和 Claude code 都是使用这种方案。」

cld「Claude code 能命中，Codex 不行。」

mintaqrua「codex 使用的 encrypted compaction 和 claude code 完全不同，不是简单的 prompt based compaction。这是 codex/gpt 目前相比竞品最大的优势之一……限制是必须 name 为 OpenAI 或 Azure，否则性能显著下降。」
