llama.cpp #27856 — Flash-Next が深さで decode 崖（HIP→CUDA議論）

https://github.com/ggml-org/llama.cpp/issues/27856

タイトル: qwen4exp (Qwen3.8-Flash-Next): severe decode slowdown beyond ~1K context on HIP / gfx1151 (Strix Halo)。PR #27742 マージ後のビルドでも、文脈深さだけで decode が崩れる、という報告。品質は 45K needle でも正確。prefill も落ちるが本丸は generation。

最初の数字（報告者）

AMD Strix Halo（Ryzen AI Max+ 395 / gfx1151 / 128GB unified）: 短プロンプト ~19–21 tok/s → 合計文脈 ~1K 超で急落 → ~2K 以降 5.5–6.1 tok/s（45K で ~4.6）。CUDA では減衰は穏やか、という前提で HIP 特異を疑っていた。

コメントの応酬

続報1: 本番サーバでも 6.1K prompt で 5.65 tok/s、4分超でクライアント timeout。メモリ圧はゼロ。CPU でも長文脈 7.71 tok/s というコミュニティ測定があり、「QSA indexer → top_k → gather が CUDA 以外で遅い汎用パス」仮説。

続報2（CUDA）: DGX Spark / GB10 で llama-bench --n-depth をやり直すと、IQ1_S tg128 が d0 37.12 → d32K 23.98 → d131K 11.18（-70%）。「mild」前提は崩れる。#27742 マージは prefill を大きく上げたが decode@depth はむしろ微悪化、とも。

続報3（原因候補）: #27874 / #27865 側。HIP で GGML_CUDA_USE_CUB 無しだと TOP_K/ARGSORT が ne[0]≤1024 で打ち切られ、QSA の ggml_top_k（毎トークン・12層）が CPU fallback + 同期。閾値 ~1K と崖が一致。hipCUB パッチ後は 18K でも ~20 tok/s 台を維持、との検証コメント。

体験

Issue 本文と埋め込みコメントを読んだ。#27742 は指示どおりスキップ（既報）。ベンチは未再現。
