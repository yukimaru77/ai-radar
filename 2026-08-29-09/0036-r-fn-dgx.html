Qwen3.8-FN 2×DGX Spark 181 tok/s agg @512K

https://www.reddit.com/r/LocalLLaMA/comments/1w1486l/

r/LocalLLaMA の StartupTim。2× DGX Spark 上の Qwen3.8-Flash-Next で、512K 文脈・複数エージェント共有時に aggregate 181 tok/s を出した、というレポート。こちらはベンチしていない——投稿の数字と条件をそのまま残す。

Today I hit 181 toks/s (aggregate) on Qwen3.8-Flash-Next on 2x DGX Sparks

181 tok/s aggregate… Single-stream decode is 30–50 tok/s — the 181 is total throughput with ~9 concurrent agent sessions sharing the engine. I actually peaked to 195 while writing this.

条件

・HW: 2× NVIDIA DGX Spark（GB10、各128GB unified、20-core ARM）。ConnectX-7 直結、NCCL over RDMA（RoCE 200Gb）、TP=2。Using network IB をログで確認せよ——TCP フォールバックは静かで速度半減、と警告。
・モデル: Qwen3.8-Flash-Next、RadixArk NVFP4（4-bit routed experts、FP8 n-gram table）。ハイブリッド注意（3/4 linear + 1/4 sparse full）、512-expert MoE、MTP speculative k=3（受理~40%）。ネイティブ 262K を YaRN 2.0 で 512K（needle 487K で確認）。

We mmap it straight off NVMe instead of loading it: weights per node dropped 65 → 41 GiB

PLE（n-gram embedding）テーブルが 320M 行・FP8 で 47.7 GiB。トークンごとに触るのは 16 行（~2.5KB）なので NVMe に mmap。madvise(MADV_RANDOM) 前は 405K prefill がディスクから 603GB 読んだが、後は 19GB。64 gather threads。空いたメモリは KV へ——プール 2.89M tokens / 40.6 GiB pin。ベースは blazux/qwen3.8-Flash-DGX（Apache-2.0）を TP=2 向けに改修。

vLLM（公式 day-0 イメージ）: --kv-cache-memory 40600000000（手動 pin は --gpu-memory-utilization を無視）、--max-num-batched-tokens 8192、--long-prefill-token-threshold 4096、--enforce-eager（GB10/SM121 で CUDA graph が落ちる）、prefix caching、MTP speculative。cold long prefill の同時数を抑えるスケジューラパッチ。前面に llama-swap + nginx TLS、watchdog は earlyoom の絶対フロア（unified memory では「空きが少ない＝異常」ではない）。

負荷例は Deepseek Harness / OpenwebUI の「build a game」系。数字は著者環境の一人称。こちらは再測定していない。
