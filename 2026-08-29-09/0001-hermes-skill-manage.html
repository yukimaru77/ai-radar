Hermes skill_manage が原子バッチに

https://x.com/tonysimons_/status/2093492234624594128

自己改善ループがスキル庫を犯罪現場にする、という失敗モードに対するゲート付き自己書き換え。

skill_manage can now perform an entire batch of changes in ONE call. Create a skill. Patch another. Add files to another. Update another. And the whole thing is ATOMIC. If one operation fails? Hermes rolls the entire batch back. Self-improvement without leaving its skill library looking like a crime scene. — @tonysimons_

引用ツイート側の実装は NousResearch/hermes-agent のコミット 72874b0（2026-08-28 19:15 UTC / 翌 04:15 JST）。メッセージは feat(skill_manage): operations[] is the call — each op names its skill; atomic with cross-skill rollback (#97295)。レポ本体は別ページ。

実装が言っている境界

今日開いた tools/skill_manager_tool.py では、バッチ可能な action は create / patch / write_file / remove_file。上限は 20 ops。各 op が自分の name（スキル）を持つ。触るスキルは実行前にスナップショットされ、1つでも失敗したら触ったスキル全部をバッチ前に戻す。バッチが作ったスキルは削除。

delete はバッチに混ぜられない。そのコールの唯一の op で、単体ハンドラへルートする。理由は「recoverable-archive が他 op の rollback と合成できない」。create はそのスキルの他 op より先。同一ファイルへの破壊的 op（write_file / remove_file / SKILL.md 全文 rewrite）がバッチ内で二度当たると、先の仕事を黙って捨てるので事前 reject。additive な patch チェーンと write-then-patch は合法。パスは正規化して ./references/x.md 表記のすり抜けを塞いだ、とコミット本文。

承認ゲートはバッチ全体を 1つの pending write として積む。ライブ試験で見つかった穴は「patch の直後に同ファイルへ write/remove」「パス表記ゆれ」。1ルールにまとめた、と #97295 が書いている。
