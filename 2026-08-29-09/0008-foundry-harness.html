Foundry実測: ハーネスがランタイムより効く

https://x.com/zaycruz__/status/2093453152183877694

ランタイム比較より、ツール境界を書いたハーネスが半分の tool call を削る、という n=10 の数字。

I built a Palantir Foundry agent harness and ran it on two agent runtimes — pi and prime agent — same architecture on both. … The harness mattered more than the runtime. — @zaycruz__

三つの入口（ improvise させない）

Foundry 配送を一つの UI が端から端までやらないので、エージェントに3経路を渡し、ルーティングを文書化した。

Foundry MCP — 約80のプラットフォームツールをネイティブ化。fail-closed scope：選んだ ontology / projects / その中で発見した resource 以外はサーバに届く前に遮断。

pfoundry — 自作 Foundry CLI。MCP の確認済みギャップ：impact analysis、context selection、link-type enumeration。

公式 foundry CLI — SuperRepo ライフサイクル（manifest / validation / deploy）。

変異は全部、隔離された revertible branch。8スキルで discovery → ontology → data pipelines / ontology apps → delivery。トレースは OTel → Langfuse（session/agent/tool）。tool I/O はエクスポート前に redact（field rules、pinned pattern、URL scrub）。redaction 変更は revision、commit ではない。夜間ジョブが当日トレースを再構成し、LLM 採点、secret/PII/canary スキャン、人間レビューキュー、通ったものだけ翌日の memory page。

同じモデル、10 scoped tasks

pi + harness: 90% correct / 6.9 calls / 57s

prime + harness: 80% / 10.2 / 88s

pi bare: 70% / 12.8 / 76s（1タスクは 41 calls / 300s timeout / 答えなし）

prime bare: 40% / 22.2 / 130s

裸でも Foundry には届くが、ほとんど狩っている。ハーネスは「知っているプラットフォーム」と「推測しているプラットフォーム」の差。著者自身が Small sample: n=10, one ontology, one model と書いている。次は multi-step chaining / SuperRepo / 他スタック、数字が本物になったら出す、と。

体験

ツイート全文を一次にした。Foundry / pfoundry / Langfuse は触っていない。n=10 は再現していない。pfoundry の公開 repo はこのツイートからは特定できなかった。
