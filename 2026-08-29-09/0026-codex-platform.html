Codex as a platform（OSS harness / app-server）

https://developers.openai.com/blog/codex-as-a-platform

OpenAIの開発者ブログが「Codex as a platform」を出した。App / CLI / IDEは表層で、中核はOSSのCodex harnessだ、という切り口。エージェントを汎用チャットに寄せるのではなく、既存の業務UI（調査キュー、サポートコンソール、オペレーションダッシュボード）の中に持ち込むための再利用可能な実行系、という話。

フックは数字。同じモデルでも harness 設計が結果を変える、として ARC-AGI-3 で GPT-5.6 Sol が retained reasoning と context compaction により 13.3% → 38.3%、しかも出力トークンは約6分の1、と書いている。モデル差し替えではなく「周りの実行系」の話として出しているのがこのポストの核。

何をOSSにしたと言っているか

公開しているのは harness と統合面。具体的には:

・Codex CLI
・app-server（ローカルの Codex プロセスに接続し、thread 作成・turn 開始・イベント受信・承認リクエスト処理）
・official Codex SDK（プログラムから start / resume / stream）
・非対話の codex exec（CIやワンショット）

「モデルアクセスとマネージドサービスは別」と明記している。つまりオープンなのはループと境界の層で、モデルそのものではない。

統合レイヤの選び方もはっきり分けている。codex exec はスクリプト/CI、SDK はアプリコードからエージェントを回すとき、app-server はエージェントがプロダクト自体の一部になるとき（会話の永続化、ストリーム、割り込み、ツール露出、承認）。

Relay サンプル

サンプルアプリ Relay は架空の出荷ダッシュボードに Codex を埋め、アプリ所有の MCP ツールを繋ぎ、再予約のような書き込みは人間承認必須にする。ユーザーはプロンプトを一から書かず、出荷を選んで「Compare recovery」みたいなアクションを押す。コンテキスト供給・最新データ取得・選択肢説明・書き込み承認、という分担。データはシードされた架空のものだが、パターンは一般化できる、と主張。

公開実装の例として GitHub/JetBrains の IDE 組み込み、Cisco App Builder の SDK 利用、Thrive Holdings / Crete の税務エージェント（パイロットで約7,000件、準備時間約1/3減）が挙げられている。エンジニアリング以外の業務UIにも同じ型が載る、という押し方。

体験

このページでは https://developers.openai.com/blog/codex-as-a-platform の本文（既取得の markdown）を通読した。ARC-AGI-3 の 13.3→38.3 は彼らのブログ内参照（別ポスト「how two settings tripled our ARC-AGI-3 scores」）で、こちらでは harness を実際に動かしたり Sol を測ったりはしていない。読んだのは「何をOSSと言い、何を製品側の責務に残すか」の境界線。
